## Summary and CV traceability

We pretrain a from-scratch Masked Autoencoder (MAE) on the 50K CIFAR-10 training images without labels, then measure how much it reduces the labels a ViT-Tiny needs, against a from-scratch baseline trained under the same recipe. The project is done when each of the four CV bullets has a concrete artifact behind it that can be shown in an interview.

| 2. ViT-Tiny pretrained on 50K unlabelled images, fine-tuned at 1/10/100% vs matched from-scratch | Label-efficiency plot and table: test accuracy vs label fraction, both arms, mean ± std over seeds | `results/figures/label_efficiency.png`, `results/runs.csv` |
| 3. Shallow decoder so semantic capacity sits in the encoder | Parameter and compute split (encoder vs decoder), written justification, decoder discarded after pretraining | Architecture section below, `README.md` |
| 4. Masking-ratio ablation 50/75/90 and linear probing vs random-init frozen encoder | Table: linear-probe accuracy for MAE-50/75/90 and a random-init encoder at 1/10/100%, plus fine-tune at 1% | `results/figures/ablation.png`, `results/runs.csv` |

This is v1.0 of the August v0.1 doc. The main changes are a true 12-block ViT-Tiny (v0.1 had 6 blocks), a 4-block decoder (v0.1 had 2), and scripts from day one instead of notebook-first. Each change is explained in its own section.

## Goals, non-goals, success criteria

The goal is a clean, honest measurement, not a state-of-the-art number. A result where MAE helps a lot at 1% labels and little at 100% is a perfectly good outcome, as long as it is measured fairly.

**Goals**

- Working MAE written from scratch, with tests that prove the two mechanics that define it: random masking and a loss on masked patches only.
- A label-efficiency curve at 1%, 10% and 100% labels, with an MAE-initialised arm and a from-scratch arm that differ only in their starting weights.
- A masking-ratio ablation (50/75/90%) judged by linear probing, with a random-init frozen encoder as the floor.
- A repo anyone can rerun from the README on a free Kaggle T4.

**Non-goals (v1)**

- Other datasets (STL-10 is a later extension, as decided in August).
- Decoder-depth ablation as a headline result (one optional small check, see Architecture).
- Comparisons with SimCLR, DINO or other SSL methods.
- Matching the MAE paper's ImageNet numbers.

**Done when**

- [ ] All unit tests pass and the reconstruction grid shows plausible fills on held-out test images.
- [ ] Every run in the run matrix has a row in `results/runs.csv`.
- [ ] The three figures and two tables exist and are generated by one script from the CSV.
- [ ] The README states the result in one paragraph, including where MAE did not help.

## Why MAE works: the reasoning behind each design choice

MAE turns unlabelled images into a supervised task: hide most of the image, predict the hidden pixels. Each choice below exists to make that task hard enough that the only way to solve it is to learn what objects and scenes look like. These are the arguments to give in an interview; the MAE paper (He et al., 2021) is the source for each.

**1. Mask a lot (75%).** Images are highly redundant: a missing patch can usually be filled by blurring its neighbours. With 25% hidden, the model can win by interpolation and learns little. With 75% hidden, whole object parts are gone, so the model must infer them from what the object is. This differs from BERT's 15% because words carry far more information each than pixels do.

**2. Random, uniform masking.** Patches are hidden uniformly at random per image. This avoids a centre bias and stops the model from relying on fixed positions always being visible.

**3. Encoder sees only visible patches (asymmetric design).** Masked patches are dropped, not replaced by a \[MASK\] token in the encoder. Two reasons: the encoder runs on 16 of 64 tokens, so pretraining is about 4× cheaper in the encoder; and the encoder never sees an artificial token that will not appear at fine-tuning time, so there is no train/test mismatch.

**4. Lightweight decoder, thrown away afterwards.** The decoder adds mask tokens back, restores patch order, and predicts pixels. Only the encoder is kept for downstream tasks, so the decoder should be just strong enough to turn the encoder's features into pixels and no stronger. Detail and the caveat are in the Architecture section.

**5. Loss on masked patches only.** Visible patches can be reconstructed almost by copying their input through the network. Including them in the loss rewards that copying and dilutes the gradient from the hard part. The paper reports lower accuracy when the loss covers all patches.

**6. Per-patch normalised pixel targets.** Each target patch is normalised by its own mean and standard deviation before the MSE. This removes brightness and contrast, so the loss is about edges and structure rather than average colour. The paper found this improves downstream accuracy.

The pretraining loss, with M the set of masked patches, p̂ the prediction and p̃ the normalised target patch (48 values for a 4×4×3 patch):

```latex
\mathcal{L} = \frac{1}{|M|} \sum_{i \in M} \frac{1}{48} \left\lVert \hat{p}_i - \tilde{p}_i \right\rVert_2^2, \qquad \tilde{p}_i = \frac{p_i - \mu(p_i)}{\sqrt{\sigma^2(p_i) + 10^{-6}}}
```

**Why a ViT and not a CNN?** A ViT treats an image as a set of tokens, so dropping 75% of them is just indexing. A CNN slides over a dense grid and cannot skip masked regions without sparse convolutions or mask tokens, which reintroduces the mismatch in point 3.

## Data and splits

Pretraining uses all 50,000 CIFAR-10 training images with labels ignored. The 10,000 official test images are used only for the final reported numbers, never for choosing anything.

**Label fractions.** For each fraction and seed, draw a class-balanced subset of the training set. The labelled subset is split again into train and validation (val = 10% of the subset, at least 10 per class). Both arms use exactly the same subset and split for a given seed, so the comparison is paired.

| Fraction | Labelled images | Per class | Train / val | Seeds |
| --- | --- | --- | --- | --- |
| 1% | 500 | 50 | 400 / 100 | 3 |
| 10% | 5,000 | 500 | 4,500 / 500 | 1 |
| 100% | 50,000 | 5,000 | 45,000 / 5,000 | 1 |

Why val comes out of the labelled fraction: in a real label-scarce setting you do not get a large clean validation set for free. Carving it from the 1% subset keeps the claim honest ("1% labels" really means 500 labelled images in total). Seed i fixes both the subset draw and the training randomness, so variance across seeds covers both sources.

Splits are generated once by `scripts/make_splits.py` and saved as index files (`splits/frac{1,10,100}_seed{0,1,2}.json`) committed to the repo. Every run loads indices from these files, so no run can draw a different subset by accident.

**Is pretraining on the same 50K images leakage?** No. Pretraining sees pixels only, never labels, and never the test set. This is the standard semi-supervised setup: all images are available, few labels are.

**Augmentations.**

| Stage | Augmentations | Why |
| --- | --- | --- |
| Pretraining | RandomResizedCrop(32, scale 0.2–1.0), horizontal flip | The MAE paper uses only crop and flip; masking itself is the main augmentation |
| Fine-tuning (both arms) | RandomCrop(32, pad 4), flip, RandAugment(2, 9), label smoothing 0.1 | ViTs overfit small data without strong augmentation; applied identically to both arms |
| Linear probe | None (centre image, cached features) | Measures the frozen features as they are |

Normalisation uses the CIFAR-10 channel mean and std for model inputs. The pretraining target uses the per-patch normalisation from the previous section.

## Architecture

The encoder is a standard ViT-Tiny (12 blocks, width 192, 3 heads) on 4×4 patches; the decoder is 4 blocks at width 128 and has about 15% of the encoder's parameters. A pipeline diagram follows at the end of this section.

| Component | Setting | Why |
| --- | --- | --- |
| Patches | 4×4 px → 8×8 = 64 tokens, 48 values each | Standard for 32 px ViTs; patch 2 gives 256 tokens and about 4×+ the cost |
| Patch embedding | Linear 48 → 192 (written as a strided conv) | Same as the ViT paper |
| Position embedding | Fixed 2D sin-cos, not learned | Used by MAE; nothing to learn, and it gives the decoder reliable positions for mask tokens |
| Encoder | 12 pre-norm blocks, width 192, 3 heads, MLP 768, final LayerNorm | This is what "ViT-Tiny" means (DeiT-Ti); v0.1's 6 blocks would not justify the name |
| Class token | None; classifier uses mean of patch tokens | Simpler masking code; the MAE paper reports mean-pooling works as well as a class token |
| Masking | Per image: random noise → argsort → keep first 16 of 64 (75%) | Uniform random masking with no loops; the same indices restore order later |
| Decoder | Linear 192 → 128, add mask tokens, unshuffle, add pos-embed, 4 blocks width 128 (4 heads), LayerNorm, linear 128 → 48 | Narrow and shallow: cheap, and discarded after pretraining |
| Classifier (downstream) | Encoder on all 64 tokens → mean-pool → LayerNorm → Linear 192 → 10 | Same head for both arms |

**Size and compute** (multiply-accumulates for the main matrix products, per image):

| Part | Parameters | Pretraining compute | Share of pretraining compute |
| --- | --- | --- | --- |
| Encoder (16 visible tokens) | 5.35 M | 86 M MACs | 61% |
| Decoder (64 tokens) | 0.82 M | 55 M MACs | 39% |
| Encoder at fine-tune (64 tokens) | same 5.35 M | 359 M MACs | n/a |

**Why the decoder is shallow (CV bullet 3), and the caveat.** Three arguments support a small decoder. It is thrown away, so every parameter there is spent on something we do not keep. Because the encoder only sees visible patches, everything the decoder knows about the image has to come through the encoder's output, so understanding must live in the encoder. A narrow 128-wide decoder cannot memorise its way to good reconstructions on its own.

The caveat: the MAE paper found that a decoder that is too shallow (1 block) hurts linear probing. The last encoder blocks then have to specialise in pixel reconstruction instead of semantics. That is why this design uses 4 blocks, not 1 or 2 as in v0.1: shallow relative to the 12-block encoder, but deep enough to take over the pixel-level work. Say this nuance in interviews; it shows you understand the trade-off rather than repeating a slogan.

**Optional check (only if time remains):** a 100-epoch pretrain with a 1-block decoder versus a 4-block decoder, compared by linear probe at 100% labels. One extra short pretrain, no new code.

**Written by hand vs borrowed.** Model, masking, loss, position embedding and training loops are written from scratch. `torch.nn.MultiheadAttention` is avoided too: attention is written out with `F.scaled_dot_product_attention` for speed. Only torchvision is used, for dataset loading and RandAugment.

The decoder exists only during pretraining. Every downstream arm, including from-scratch, enters through the same encoder slot and is scored on the same splits.

## Pretraining recipe

MAE-75 is pretrained for 400 epochs and reused by every main fine-tuning run; MAE-50 and MAE-90 get 200 epochs each for the ablation. The recipe follows the MAE paper, scaled down to CIFAR.

| Setting | Value | Why |
| --- | --- | --- |
| Epochs | 400 | MAE keeps improving with long schedules; 400 fits the compute budget (v0.1 decision) |
| Batch size | 512 | Fits a T4 easily with 16 visible tokens; about 98 steps per epoch |
| Optimiser | AdamW, betas (0.9, 0.95), weight decay 0.05 | MAE paper settings; beta2 0.95 is more stable for ViTs than 0.999 |
| Learning rate | 1.5e-4 × batch / 256 = 3e-4 peak | MAE's linear scaling rule |
| Schedule | 20 warm-up epochs, then cosine to 0 | Warm-up avoids early instability in attention |
| Precision | fp16 autocast + GradScaler | T4 has fast fp16 but no fast bf16 |
| Loss | MSE on masked patches only, normalised-pixel targets | See the reasoning section |
| Checkpoints | Every 25 epochs plus final; resume from latest | Kaggle sessions can stop; resuming must be exact (model, optimiser, scaler, scheduler, epoch, RNG) |

**Learning-rate sanity check.** Before the full run, train 20 epochs at 3e-4 and at 1e-3 and keep the one with lower reconstruction loss. This only guards against a badly mis-set rate; it is not tuning for downstream accuracy.

**What gets logged per epoch:** train loss, learning rate, epoch time, GPU memory. Every 50 epochs, a reconstruction grid on 8 fixed test images (original, masked input, prediction pasted into the visible patches). The grids are the quickest proof that bullet 1 works.

**Time per run** is unknown until measured. Milestone 1 times 5 epochs and the run matrix is updated with the real number. The plan assumes 1–2 hours per 400-epoch run on a T4.

## Fine-tuning protocol: MAE vs matched from-scratch

The two arms differ in exactly one thing: the MAE arm starts from the pretrained encoder, the scratch arm from random weights. Data subset, augmentation, step budget, optimiser and learning-rate sweep are the same. That single difference is what makes "matched" a defensible word on the CV.

**Shared recipe.** AdamW (betas 0.9, 0.999), weight decay 0.05, 5% linear warm-up then cosine, stochastic depth 0.1, label smoothing 0.1, fp16. The whole network is trained (full fine-tuning).

**Step budget per fraction** (identical for both arms):

| Fraction | Train images | Batch | Steps | Approx. epochs |
| --- | --- | --- | --- | --- |
| 1% | 400 | 64 | 3,000 | 480 |
| 10% | 4,500 | 128 | 6,000 | 170 |
| 100% | 45,000 | 256 | 17,600 | 100 |

Budgets are set in steps, not epochs, because 1% has so few images that "100 epochs" would be only about 600 updates. The budget must be long enough for the scratch arm to plateau; if its val curve is still rising at the end, extend both arms equally.

**Learning-rate sweep.** For each arm and fraction, try {5e-4, 1e-3, 2e-3} on seed 0. Pick the best by val accuracy, then run the remaining seeds at that rate. Each arm gets its own best rate, so neither is handicapped by a rate tuned for the other.

**Model selection and reporting.** Keep the checkpoint with the best val accuracy, then evaluate it once on the 10K test set. Report test accuracy as mean ± std across seeds, plus the paired gain (MAE minus scratch on the same seed).

**Deliberately left out: layer-wise learning-rate decay.** The MAE paper fine-tunes with it, but it only makes sense for pretrained weights. Using it would make the arms differ in two things, not one. It is listed as a possible extra in Future work.

**What we expect, stated as a hypothesis:** the gain from MAE is largest at 1% and shrinks as labels grow, because with 45K labels the scratch model can learn good features on its own. Whatever the outcome, it is reported as measured.

## Linear probing and the random-init control

Linear probing freezes the encoder and trains only a linear classifier on its features. It answers a narrower question than fine-tuning: how much class information is already in the features, before any labels touch the encoder.

**Protocol.**

1. Run the frozen encoder on all 64 patches (no masking) of each image, mean-pool, and cache the 192-d feature to disk. No augmentation, so this happens once per encoder.
2. Train BatchNorm (no affine) followed by Linear 192 → 10 on the cached features, using the same label subsets and splits as fine-tuning.
3. AdamW, 100 epochs, learning-rate sweep {1e-3, 1e-2, 1e-1} chosen on val, report test accuracy.

BatchNorm without learnable scale normalises feature scales, which the MAE paper does because MAE features vary widely in magnitude. It is still a linear classifier: at test time it is a fixed affine map.

Because features are cached, each probe takes seconds. That makes it cheap to probe every encoder at every fraction and seed.

**Encoders probed.**

| Encoder | Role |
| --- | --- |
| Random-init, frozen | Control: what a linear layer gets from an untrained network |
| MAE-50 | Ablation |
| MAE-75 | Main model |
| MAE-90 | Ablation |

**Why the random-init control matters.** A random network is not useless: random projections of patches already separate some classes, partly by colour. A probe reaching some accuracy proves nothing alone. Pretraining is credited only with the gap above this floor. Without the control, bullet 4 is not "validated", only measured.

**Expected and honest caveat.** MAE features are known to be less linearly separable than those of contrastive methods; MAE shines under fine-tuning. A modest probe score with a clear gap over random init is the expected, explainable result.

## Masking-ratio ablation (50 / 75 / 90%)

The ablation checks whether 75% is a good choice at CIFAR scale rather than taking the paper's ImageNet result on trust. Everything except the masking ratio is held fixed: same architecture, epochs, batch, learning rate and seed.

**Epoch budget.** To fit 3–4 days, MAE-50 and MAE-90 are pretrained for 200 epochs. They are compared with MAE-75's epoch-200 checkpoint, which is saved anyway, not its final 400-epoch weights, so epochs stay equal across the ablation. Main results still use MAE-75 at 400 epochs.

| Ratio | Visible tokens (of 64) | Encoder compute vs 75% | What it tests |
| --- | --- | --- | --- |
| 50% | 32 | about 2× | Is the task too easy, solvable by interpolation? |
| 75% | 16 | 1× | Main setting |
| 90% | 6 | about 0.4× | Is too little left to infer from at 32 px? |

**How each ratio is judged.**

- Linear probe at 1%, 10% and 100% for every seed (cheap, cached features). This is the main ablation metric, as in the paper.
- Full fine-tuning at 1% only, 3 seeds, using the learning rate chosen for MAE-75 at 1%. The 1% setting is where pretraining matters most and runs are short.
- Reconstruction grids at the same 8 test images, for a visual comparison.

**Not used as a metric: reconstruction loss.** Lower loss at 50% masking does not mean better features: the task is simply easier. The paper's point is that a harder pretext task gives better representations.

**Hypothesis.** 75% beats 50% on linear probe. 90% may also trail 75% here: with only 6 of 64 patches visible at 32 px, a lot of the image is unrecoverable, which is different from ImageNet's 224 px with 49 visible patches. Either result is reportable and explainable.

## Run matrix and compute budget

The full plan is 3 pretrains (one at 400 epochs, two at 200), 28 fine-tuning runs and 75 linear probes, an estimated 6–9 T4 GPU-hours. The hour figures are estimates until Milestone 1 measures real epoch times, and this table gets updated then.

| Block | Runs | Count | Est. GPU-hours |
| --- | --- | --- | --- |
| Pretrain LR check | MAE-75, 20 epochs, at 3e-4 and 1e-3 | 2 | 0.2 |
| Pretrain, main | MAE-75, 400 epochs (epoch-200 checkpoint kept for the ablation) | 1 | 1–2 |
| Pretrain, ablation | MAE-50 and MAE-90, 200 epochs each | 2 | 1–2 |
| Fine-tune LR sweep | 2 arms × 3 fractions × 3 LRs, seed 0 | 18 | 3–4 |
| Fine-tune extra seeds | 1%: seeds 1 and 2 × 2 arms | 4 | 0.2 |
| Fine-tune ablation | MAE-50, MAE-90 at 1%, 3 seeds | 6 | 0.3 |
| Linear probes | 5 encoders (random, MAE-75 at 400, and MAE-50/75/90 at 200) × 5 subsets × 3 LRs, cached features | 75 | under 0.2 |
| Optional decoder check | Only if a day is left over | 1 | 0.5 |

The 100% fine-tuning runs dominate the fine-tuning cost; everything at 1% and 10% is short.

**Running on Kaggle.** Long pretrains run as "Save & Run All" background sessions so the browser can be closed. Checkpoints go to `/kaggle/working` and are published as a Kaggle Dataset, so fine-tuning notebooks can attach them. Short runs are batched several per session to avoid repeated setup. Check your current weekly GPU quota on Kaggle before starting; this plan should fit inside one week's quota with room for reruns.

**Order matters.** MAE-75 pretrain runs first and alone; fine-tuning on 1% and 10% starts as soon as it finishes. The 50% and 90% pretrains run while the fine-tuning work is being analysed.

## Codebase, tooling, reproducibility

The code is plain Python scripts driven by small YAML configs; Kaggle notebooks only clone the repo and call the scripts. This replaces v0.1's notebook-first plan: with a deadline, refactoring later is wasted time, and scripts are easier to defend in a code walkthrough.

```
mae-label-efficiency/
  configs/            pretrain_m50.yaml, pretrain_m75.yaml, pretrain_m90.yaml, finetune.yaml, probe.yaml
  splits/             frac1_seed0.json ... frac100_seed0.json   (committed)
  src/mae/
    data.py           CIFAR-10 loading, split loading, transforms
    pos_embed.py      2D sin-cos position embedding
    vit.py            PatchEmbed, Attention, MLP, Block, ViTEncoder, ViTClassifier
    mae.py            random_masking, MAE (encoder + decoder + loss), patchify/unpatchify
    utils.py          seeding, cosine schedule, checkpoint save/resume, CSV logger
  scripts/
    make_splits.py    pretrain.py    finetune.py    probe.py    make_figures.py
  tests/
    test_shapes.py    test_masking.py    test_loss.py    test_resume.py
  notebooks/
    kaggle_pretrain.ipynb   kaggle_finetune.ipynb   (thin wrappers)
  results/
    runs.csv          figures/
  README.md
```

**Tracking.** One CSV row per run: run id, git commit, config name, arm, ratio, fraction, seed, learning rate, best val accuracy, test accuracy, wall time. Per-epoch logs go to `results/logs/<run_id>.csv`. This is the "light tracking" chosen in August; no W&B dependency.

**Reproducibility rules.**

- Every run sets Python, NumPy and torch seeds from the config seed and logs the git commit.
- `torch.backends.cudnn.benchmark` stays on for speed; exact bit-for-bit repeats are not promised, seed variance is reported instead.
- `make_figures.py` builds every figure and table from `runs.csv` alone, so results can never drift from the logged numbers.

**Final deliverables in the repo.** README with the result paragraph, the label-efficiency plot, the ablation table, the reconstruction grids, and a one-command reproduction section.

## Sanity checks, risks and mitigations

Most MAE bugs train without crashing and just give worse numbers, so correctness is checked by tests before any long run.

**Tests that must pass before the first 400-epoch run.**

| Test | What it proves |
| --- | --- |
| `unpatchify(patchify(x)) == x` | Patch order and pixel layout are consistent |
| Masking keeps exactly 16 of 64 tokens; restore indices undo the shuffle | Masking and unshuffle are correct |
| Masks differ across images in a batch and across calls | Masking is random per image, not shared |
| Changing target pixels of visible patches leaves the loss unchanged | Loss covers masked patches only (CV bullet 1) |
| Overfit one batch of 64 images to near-zero loss in a few hundred steps | Model, loss and optimiser are wired correctly |
| Save at epoch 3, resume, compare to an uninterrupted run | Resume works before Kaggle needs it |

**Risks.**

| Risk | Sign | Mitigation |
| --- | --- | --- |
| Scratch baseline undertrained, inflating MAE's gain | Scratch val accuracy still rising at the end | Extend budget for both arms; show val curves in README |
| Too few val images at 1% (100) | Val choice flips between seeds | Report test mean ± std over 3 seeds; say so in the README |
| Pretraining loss falls but features are poor | Linear probe near the random-init floor | Check grids and probe at epoch 100 before letting the run finish |
| Kaggle session ends mid-run | Run stops before 400 epochs | Checkpoint every 25 epochs; resume test above |
| Compute runs over budget | Measured epoch time far above estimate | Sweep only 2 LRs at 100%, then cut MAE-75 to 300 epochs; never drop a main arm |
| fp16 overflow or NaN loss | Loss becomes NaN | GradScaler, LayerNorm eps 1e-6, clip gradients at 1.0 if it recurs |
| MAE does not beat scratch at 100% | Gap near zero at 100% | Expected and reportable; the claim is about label efficiency at low fractions |

## Interview defence

These are the questions an ML interviewer is most likely to ask about this CV entry, with the short answer this design supports. Fill in the measured numbers once results exist.

| Question | Short answer |
| --- | --- |
| Why 75% masking and not 15% like BERT? | Pixels are redundant; at low ratios the model fills gaps by interpolation. 75% removes whole parts, so it must model objects. My ablation measured this at 32 px: \[result\]. |
| Why compute the loss only on masked patches? | Visible ones can be copied through; including them rewards copying. I have a unit test that changes visible targets and shows the loss does not move. |
| Why doesn't the encoder see mask tokens? | Compute (16 of 64 tokens) and no train/test mismatch: at fine-tuning the encoder never sees an artificial token. |
| Why a shallow decoder? Doesn't the paper say deeper helps linear probing? | It is discarded and narrow, so understanding must sit in the encoder. But 1 block forces the last encoder layers to specialise in pixels, so I used 4: shallow relative to 12, not minimal. |
| How do you know the baseline wasn't just undertrained? | Same subset, augmentation, step budget, own LR sweep for each arm, and I checked the scratch val curve had plateaued. |
| Why did you use the same 50K images for pretraining and fine-tuning? | Pretraining sees no labels and never the test set; that is the standard semi-supervised setting. |
| What does the random-init control tell you? | A frozen random network already gets above chance from colour and patch statistics. Pretraining is credited only with the gap above it: \[result\]. |
| Why is MAE's linear-probe accuracy lower than its fine-tuning accuracy? | MAE features are rich but not linearly organised by class; fine-tuning reshapes them. Contrastive methods probe better, MAE fine-tunes better. |
| Why ViT instead of ResNet? | Masking is just dropping tokens in a ViT. A CNN needs dense input, so it would need mask tokens or sparse convs. |
| Why per-patch normalised targets? | Removes brightness and contrast, so the loss focuses on structure; the paper found it improves accuracy. |
| How many seeds, and why different counts? | 3 at 1%, 1 each at 10% and 100%. Variance is largest with few labels; with more time I would add seeds at 10%. |
| What would you do next? | STL-10 at 96 px, decoder-depth ablation, layer-wise LR decay, longer pretraining, and a SimCLR comparison. |

**Numbers to know by heart:** encoder 5.35M params, decoder 0.82M (about 15%), 64 patches of 4×4, 16 visible at 75%, 400 pretraining epochs, 500 labelled images at 1%, and your three headline test accuracies per arm.

## Milestones

Four days, planned so the GPU is busy while code is being written. Each step ends at a gate that must pass before the next long run, so a bug never costs a 400-epoch run.

1. **Day 1: setup, model, tests, start MAE-75.** Repo skeleton, splits, `vit.py` written fresh, `mae.py`, all sanity tests, a 5-epoch timing run, the 20-epoch LR check. Launch MAE-75 (400 epochs) as a background Kaggle session overnight. *Gate:* all tests pass, one-batch overfit works, splits are class-balanced.
2. **Day 2: downstream code, short runs.** Write `finetune.py` and `probe.py`, test them on MAE-75's epoch-100 checkpoint. When MAE-75 finishes, run the 1% and 10% sweeps and the 1% extra seeds; launch MAE-50 and MAE-90 (200 epochs). *Gate:* reconstruction grids look plausible and the epoch-100 probe beats random init.
3. **Day 3: 100% runs, probes, ablation.** 100% sweeps for both arms, all linear probes, 1% ablation fine-tunes. *Gate:* scratch val curves have plateaued; every run is in `runs.csv`.
4. **Day 4: results and write-up.** `make_figures.py`, README with the result paragraph, fill the \[result\] slots in Interview defence. *Gate:* every "Done when" box at the top is ticked.
